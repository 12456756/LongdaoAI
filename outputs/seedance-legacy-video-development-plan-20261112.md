# Seedance 旧接口适配开发方案

版本：2026-11-12，包含第一部分“图生视频参考图片的本地存储与临时访问”、第二部分“创建请求与状态查询的协议转换”和第三部分“视频下载适配”。

状态：开发设计，尚未实施。本文不代表线上已经具备相关功能。本次只新增方案文档，不修改业务代码、服务器配置或 SEP。

## 1. 本次确定的要求

1. SEP 继续通过 Longdao 的 `POST /v1/videos` 提交生成请求；图生视频继续上传 `input_reference` PNG 文件。
2. 图片必须保存在 Longdao 所在服务器的持久磁盘上。本部分不引入云对象存储或 MinIO 服务。
3. Longdao 提供脑生云可通过公网 HTTPS 获取的图片 URL，在转接旧接口时使用，图片角色按本次需求设置为 `reference_image`。
4. Longdao 的参考图片、签名 URL、Redis 图片记录均采用 7 天期限。
5. 视频任务与原 Key、分组、上游账号的关联继续保存在 Redis，不增加任务绑定数据库。
6. 第一部分定义图片流程；第二部分从第 18 节开始，定义创建请求与状态查询转换；第三部分从第 31 节开始，定义视频下载适配。本文为开发设计，不代表功能已经实施或通过端到端验收。
7. 计费结算沿用当前机制；原有已受理任务失败或取消后的退款、对账等待等处理边界，本轮暂不调整。适配仍须正确传递原计费字段，避免重复创建或重复计费。

## 3. 调研结果：已有系统怎样提供临时文件 URL

本次核对了以下一手资料。这里说明的是成熟项目中实际存在的实现模式，不作“全行业使用率最高”的推断。

| 来源 | 已有做法 | 对本项目的启示 |
|---|---|---|
| OWASP 文件上传指南 [R1] | 上传文件放在 webroot 外；通过应用处理器把资源编号映射到文件；使用服务端生成的随机文件名 | 本地目录不直接公开，访问必须经过专用处理器 |
| Laravel `UrlGenerator` 源码 [R2] | `temporarySignedRoute` 使用过期参数；签名时使用 HMAC-SHA256；请求时重新计算并校验签名、检查是否过期 | 可以为应用路由生成有期限且可校验的链接，无需使用对象存储 |
| Django 签名文档 [R3] | 使用签名保护数据，`TimestampSigner` 可以校验签名年龄；列出了临时访问受保护下载资源的用途 | 带时间限制的签名访问是成熟框架已经采用的方式 |
| Nginx `secure_link` 官方模块 [R4] | 校验链接真实性，支持有效期；官方配置需要相应模块，使用其规定的摘要格式 | 由反向代理验证链接也是已有方案，但接入时需要 Nginx 配置与模块支持 |
| Go `crypto/hmac` 文档 [R5] | 标准库提供 HMAC，示例使用 SHA-256，并要求使用 `hmac.Equal` 比较签名 | Go 项目可以使用标准库实现框架中已经采用的签名机制 |

本项目确定使用：**本地私有目录 + 应用层临时签名 URL + Go 标准库 HMAC-SHA256 验签 + Redis 图片记录**。

选择依据是当前工程已有 Caddy、Go 应用和 Redis；应用本来就需要读取 Redis 验证图片记录，并可直接读取持久目录。该方式无需另部署 Nginx 或对象存储服务。它采用 [R1][R2][R3][R5] 已有机制。

需要区分：HMAC-SHA256 不是本项目发明的算法；下文的路由名、Redis 字段名、签名参数和序列化规则是本项目需要明确的接口约定，不宣称它们是统一行业协议，也不宣称与 Laravel 或 Django 的 URL 格式直接互通。

## 4. 本地图片保存在哪里

### 4.1 持久目录

拟新增以下挂载，不写入容器可写层或临时目录：

| 位置 | 拟定路径 | 用途 |
|---|---|---|
| 服务器宿主机 | `/www/longdao/media/video-inputs` | 实际图片与少量清理元数据 |
| Longdao 容器内部 | `/app/media/video-inputs` | 应用读取、写入和清理图片的路径 |

容器路径通过 bind mount 指向宿主机路径。blue、green 必须挂载同一宿主机目录，容器重建或切色不删除原图片。具体挂载写入当前华为云发布入口管理的配置，不直接使用已经标记为旧部署方式的生产 Compose。[C5]

图片目录不能配置成 Caddy `file_server` 或其他可绕过鉴权的公开静态目录。公网只能访问后文的图片处理接口。[R1]

目录权限拟设为 `0700`，文件权限为 `0600`，所有者与应用实际运行的 UID/GID 匹配。部署时检查真实用户，不能假定容器以 root 运行。

### 4.2 图片路径与命名

```text
/www/longdao/media/video-inputs/
  2026/11/12/
    vref_<随机 UUID 的 32 位小写十六进制字符>/
      input.png
      manifest.json
```

`asset_id` 使用 `vref_` 加随机 UUID，唯一标识 Longdao 保存的一份参考图；它不是 SEP 的 `referenceId`，也不是视频 `task_id`。使用已有 UUID 依赖生成，不使用用户文件名、提示词或可递增的任务编号作为路径。[R1][C6]

`input.png` 保存原始 PNG 字节。首版不压缩、缩放或重新编码，避免改变参考内容及 SEP 已计算的文件摘要。

`manifest.json` 只保存清理与校验需要的信息：格式版本、`asset_id`、`created_at`、`expires_at`、`sha256`、`byte_length`。不保存签名密钥、完整签名 URL、API Key 明文或 SEP 用户身份。它用于 Redis 不可用时仍能判断磁盘文件是否该删除，不是一套新的任务数据库。

同一张图片被不同请求上传时，首版分别保存，不做跨 Key 的全局文件复用。

## 5. 保存期限：统一 7 天

### 5.1 起算点

图片校验通过、准备发布成有效参考图时，Longdao 生成统一的 `created_at`，记为 `T0`，使用 UTC Unix 秒。

```text
有效期 = 7 × 24 × 60 × 60 = 604800 秒
expires_at = T0 + 604800
```

同一份图片的文件清理时间、URL 到期时间和 Redis 图片记录的到期时间，共用这一份 `expires_at`。保存 Redis、补填任务 ID 或读取图片都不重新计算“从现在开始 7 天”。

| 内容 | 期限 | 到期后的行为 |
|---|---|---|
| 图片文件 | 自 `T0` 起 7 天 | 立即失去下载资格，进入磁盘清理范围 |
| 签名 URL | 与图片相同的 `expires_at` | 当服务器时间达到该值时，拒绝新的下载请求 |
| Redis 图片记录 | 到相同 `expires_at` | 使用绝对过期时间，避免不同操作造成期限漂移 |
| 已有视频任务路由绑定 | 仍为任务被上游接受并建立绑定后的 7 天 | 延续当前实现，与图片上传起算点有所不同 |

“7 天到期”不等于磁盘恰好在某一秒完成删除：接口按绝对时间拒绝新请求；正常情况下定时任务在到期后的下一轮清理文件。已经在到期前通过校验并开始传输的请求允许完成，不承诺在到期那一秒中断网络流。

本部分的 7 天规则针对 Longdao 新增参考图片链路。SEP 当前上传引用的 15 分钟缓存和成品视频的 24 小时缓存是另一层本地机制，本次不修改；Longdao 已取得并落盘的图片不受 SEP 那份缓存到期影响。[C1]

## 6. 图片上传、校验和落盘流程

### 6.1 输入约束

| 项目 | 首版约束 |
|---|---|
| 请求入口 | 现有 `POST /v1/videos` |
| 登录与调用权限 | 继续验证原 Longdao Key、分组及现有媒体权限 |
| 文件字段 | `input_reference` |
| 图片数量 | 恰好 1 张，拒绝多个文件和重复文件字段 |
| 文件格式 | PNG，不能仅相信文件扩展名或 multipart 声明 |
| 文件大小 | 最大 `10 × 1024 × 1024` 字节，即 10 MiB |
| multipart 总大小 | 本方案图生分支拟限制为 12 MiB，给表单字段及封装保留空间；同时受更小的现有全局限制约束 |
| 宽高上限 | 各不超过 4096，像素总数不超过 16777216，作为首版拟定限制 |
| 文件名 | 由 Longdao 生成；客户端原文件名不参与路径拼接 |

10 MiB 与 SEP 当前上传约束一致。Longdao 自己也必须校验，不能依赖所有调用者都经过 SEP。尺寸上限是本项目约束，实施时还要与启用的 SEP Profile 及上游模型要求对齐。[R1][C1]

### 6.2 执行顺序

1. 在读取图生请求体前校验现有 Key 与分组权限，设置请求总大小限制并取得上传并发名额；模型和报价检查在解析出必要字段后完成，全部通过后才允许提交上游。
2. 首版沿用当前 Handler 有界读取请求体的结构。在同一持久文件系统内创建独占暂存目录，将解析出的受限 PNG 分块写入，避免额外复制成多个完整缓冲区。这不是从网络到磁盘的全程流式上传。
3. 校验实际字节数、PNG 文件内容、尺寸及解码结果。仅检查 MIME 或 PNG 开头几个字节不算校验完成。写入时计算 SHA-256，图片解码设置并发上限。[R1]
4. 生成 `asset_id`、`T0` 和 `expires_at`，写入清理清单；关闭文件并完成必要的同步。
5. 将暂存目录原子发布到最终目录。发布前的半成品不能被下载接口读取，目标已存在则拒绝覆盖。
6. 生成第 7 节规定的签名 URL，原子登记 Redis 图片记录并设置绝对过期时间。
7. 确认文件与 Redis 登记均成功后，才将图片 URL 放入旧接口内容，图片角色使用 `reference_image`，提交给脑生云。
8. 收到上游任务编号后，将 `task_id` 补入图片记录，建立现有任务路由绑定，再按视频接口契约响应 SEP。

必须先完成文件发布和 Redis 登记，再调用上游：脑生云可能在创建响应返回之前就请求图片，所以下载接口不能要求 `task_id` 已有值。

整个过程不把 SEP 的 `referenceId` 当成上游可用的图片地址，也不要求脑生云携带 SEP 登录信息或 Longdao API Key。

## 7. 图片 URL 怎样生成，签名怎样计算

### 7.1 新增读取路由

```http
GET /media/video-inputs/{asset_id}.png?expires=<Unix秒>&kid=<密钥版本>&signature=<签名>
```

允许 `HEAD` 使用同一个有效链接获取文件头；其他方法返回 `405`。该路由定义在 `/v1` 的 API Key 鉴权路由组之外，使用专用的签名鉴权。当前 `/v1` 组使用 Key 中间件，直接把图片接口挂在其中会导致上游无法直接读取。[C4]

最终 URL 的外部形式为：

```text
https://ai.longdaoec.com/media/video-inputs/vref_<随机编号>.png?expires=<到期时间>&kid=v1&signature=<64位十六进制签名>
```

这是本地文件对应的应用接口 URL，不是文件系统路径，不是 S3 URL，也不是脑生云创建的 URL。

### 7.2 签名密钥

拟新增一组独立的服务端签名密钥：

| 配置 | 用途 |
|---|---|
| 当前 `kid` | 本次生成链接使用哪个密钥版本，例如 `v1` |
| 密钥集合 | `kid` 到密钥的映射，供生成与验签使用 |

密钥使用安全随机源生成至少 32 字节，放在服务器私密部署配置或受限密钥文件中，不提交 Git，不存入 Redis，不复用 Longdao Key、上游 Key 或登录 JWT 密钥。

blue、green 使用同一组固定密钥，重启和发布时不重新生成。轮换时新链接使用新版本，旧密钥至少保留到旧版最后一条链接到期，否则现存 7 天链接会提前失效。Django 官方也提供签名旧密钥回退机制，本项目按同样的轮换原则设计。[R3]

### 7.3 待签名 URL 的规范化规则

采用 Laravel 已使用的“对未带签名的 URL 计算 HMAC-SHA256，再追加签名参数”的模式。[R2]

本项目固定以下细则，生成和验证必须使用同一个辅助函数：

1. 公网基地址来自部署配置，固定为 HTTPS；不从客户端提供的 `Host`、`X-Forwarded-Host` 或任意请求字段拼出签名地址。
2. 路径只允许规定格式的 `asset_id` 和固定 `.png` 后缀；不接受用户提供的目录路径。
3. 待签名查询参数仅包含 `expires` 和 `kid`，通过 Go `net/url` 的结构化 API 编码并排序。
4. `expires` 是无前导符号的十进制 Unix 秒；`kid` 必须来自允许的密钥版本。
5. 下载时只允许 `expires`、`kid`、`signature` 三个查询参数，每个恰好出现一次。拒绝多余参数和重复参数，避免不同解析器理解不同。
6. `signature` 本身不参加签名。

计算过程用以下伪代码表达，不是新增加密算法：

```text
unsigned_url = 固定公网基地址 + 固定资源路径 + 规范化后的 expires、kid 查询串
signature_bytes = HMAC-SHA256(指定版本的服务端密钥, unsigned_url 的 UTF-8 字节)
signature = 小写十六进制编码(signature_bytes)
signed_url = unsigned_url + "&signature=" + signature
```

Go 实现使用 `crypto/hmac`、`crypto/sha256`、`encoding/hex`、`net/url`，不能用字符串 `SHA256(secret + path)` 冒充 HMAC，不能自行设计加密算法。验证时用 `hmac.Equal` 比较解码后的签名字节。[R5]

`GET` 和 `HEAD` 由路由共同授权访问同一个签名资源，因此签名覆盖 URL，方法另行限制；不能把同一套签名用于上传、删除等修改操作。

### 7.4 签名的实际作用

修改图片编号、到期时间或密钥版本，都会改变待签名 URL，需要重新生成对应签名。客户端和脑生云没有服务端密钥，不能仅通过修改 URL 延长有效期。[R2][R5]

图片不是被签名算法加密了；原 PNG 仍保存在服务器，公网传输使用 HTTPS。签名控制的是下载请求能否通过校验。

完整签名 URL 是临时访问凭证，持有人在有效期内可以使用。不能声称只有脑生云可以访问。首版不绑定源 IP、不要求浏览器 Cookie，也不设为一次性使用，避免上游探测、排队拉取或重试时失效。

## 8. Redis 保存哪些信息

### 8.1 图片记录

拟使用独立 Redis Hash：

```text
video:reference:{asset_id}
```

| 字段 | 解释 |
|---|---|
| `schema_version` | 图片记录格式版本 |
| `asset_id` | Longdao 生成的本地图片编号 |
| `api_key_id` | 上传请求使用的 Longdao Key 数据库编号 |
| `group_id` | 本次调用使用的分组编号 |
| `relative_path` | 图片相对持久根目录的路径，不接受客户端路径 |
| `mime_type` | 固定为已验证的 `image/png` |
| `byte_length` | 实际文件字节数 |
| `sha256` | 实际图片内容摘要 |
| `width` | 实际图片宽度 |
| `height` | 实际图片高度 |
| `created_at` | 图片有效期起算时间 `T0` |
| `expires_at` | 固定的 `T0 + 604800` |
| `signing_key_id` | 生成链接使用的密钥版本，不是密钥内容 |
| `signed_url` | 完整签名 URL，按用户要求存入 Redis |
| `task_id` | 上游接受请求后返回的任务编号，提交前可以为空 |

图片内容不放 Redis，不增加 PostgreSQL 图片任务表。Redis 里也不保存 API Key 明文、上游 Key 明文或签名密钥。

首次写入 Hash 与设置 `EXPIREAT expires_at` 在事务或 Lua 中完成，避免产生没有期限的记录。补填任务编号时，使用原子检查存在后更新，保留原绝对期限，不能在键过期后通过裸 `HSET` 重建一个永久记录。Redis 官方说明了 TTL 可被刷新，因此需要明确禁止本流程主动续期。[R6]

### 8.2 与现有任务绑定的关系

```text
SEP receiptId
  -> SEP configuration.upstreamTaskId
  -> Longdao 原 Key + 原分组 + task_id 的现有 Redis 绑定
  -> 原上游 account_id

Longdao video:reference:{asset_id}
  -> 本地 PNG 路径、signed_url、expires_at
  -> task_id
```

现有任务绑定的值仍是原上游账号编号，不把原来的字符串值改成图片 JSON，避免破坏查询和下载逻辑。[C3]

Longdao 这份图片记录绑定调用 Key，不代表识别了 SEP 的具体用户；SEP 用户到本地任务的关系仍由 SEP 保存。

## 9. 脑生云下载图片时，Longdao 怎样处理

1. Caddy 将 HTTPS 请求转给 Longdao 图片处理器，不直接读取磁盘目录。
2. 限制请求方法、路径格式和查询参数数量；校验 `kid`、时间和签名格式。
3. 使用固定公网基地址与规范化函数重建待签名 URL，计算并通过 `hmac.Equal` 验签。[R5]
4. 检查当前时间严格小于 URL 的 `expires`。
5. 查询 Redis 图片记录；确认存在，且 `expires` 与记录中的 `expires_at` 一致。
6. 从受控根目录打开记录对应的普通文件；拒绝越界路径、符号链接和尺寸异常，不把 URL 中的输入直接传给文件读取函数。[R1]
7. 从已打开的文件句柄返回内容，使用 Go `http.ServeContent` 处理 `HEAD`、长度与 Range 等 HTTP 文件传输行为。[R7]

响应固定 `Content-Type: image/png`，增加 `X-Content-Type-Options: nosniff` 和 `Cache-Control: private, no-store`。代理/CDN 不得缓存该入口并绕过验签。鉴权通过之后再处理条件请求或 Range，不能通过缓存校验分支绕过鉴权。

| 情况 | 响应约定 |
|---|---|
| GET 下载成功 | `200`，Range 正常时由文件传输实现返回相应状态 |
| HEAD 成功 | `200`，返回文件头，不返回图片正文 |
| 参数缺失、重复、格式错误或签名不正确 | `403` |
| 签名正确但链接已到期 | `410` |
| 签名有效但 Redis 没有记录，或磁盘文件不存在 | `404`，内部记录具体原因 |
| Redis 暂时不可用、文件系统读取故障 | `503`，不退化为公开下载 |
| 不支持的 HTTP 方法 | `405` |

到期时间按 UTC 绝对时间判断，服务器应保持时间同步。

## 10. 7 天后怎样清理图片

Redis 到期只影响 Redis 键，不会删除服务器文件。[R6] 因此必须增加磁盘清理任务，不能仅订阅 Redis 过期通知。

正常运行时每 1 小时执行一次清理，应用启动时也执行一次补偿扫描。服务启动后创建一个长期运行的后台 Go 协程，每轮扫描结束后关闭文件、释放锁并等待下一次定时触发；服务退出时取消协程并停止定时器。图片满 7 天后立即拒绝新访问，正常情况下磁盘文件在到期后的下一轮扫描中删除：

1. 使用进程间互斥锁，避免蓝绿短暂并存时同时执行大规模清理。
2. 分批扫描参考图目录的清理清单，以清单中的 `expires_at` 为准，不依据文件最后访问时间计算保留期。
3. 当前时间达到 `expires_at` 后，删除对应 PNG 和清单，再移除空目录；删除操作可重复执行，文件已经不存在视为成功。
4. Redis 记录通常已自行过期；若还存在则校验编号与到期时间后移除。不依赖它存在才能清理文件。
5. 失败时保留错误日志和清理积压指标，下轮重试。清理失败不会恢复 URL 的访问资格。

已登记为有效资产的图片按 7 天规则保留，即使生成失败或取消，也不在首版引入复杂的提前回收逻辑。

上传中断产生的暂存目录不属于已经生效的图片：请求失败时立即回收；进程崩溃遗留的暂存目录，在启动及周期任务中按超过 1 小时且无活跃写入锁的条件回收。这里的 1 小时只针对未完成上传，不缩短有效图片的 7 天期限。

清单缺失或损坏的目录不能未经判断就递归删除，应记录并按受控孤儿文件处理规则复核。删除路径必须确认位于专用参考图根目录内，且不跟随符号链接。

## 11. 请求失败、Redis 异常与重启

| 场景 | 必须采取的处理 |
|---|---|
| 图片超限、非 PNG、解码失败 | 返回本地校验错误，不调用上游，删除暂存文件 |
| 写盘失败、磁盘配额不足 | 返回本地存储错误，不调用上游，不生成可用链接 |
| 已落盘但 Redis 首次登记失败 | 不提交上游，回收本次文件；清理任务兜底 |
| Redis 登记成功，但上游明确拒绝 | 按接口契约返回失败，图片沿原期限保留，记录拒绝原因 |
| 创建请求超时，不确定上游是否受理 | 保留图片及原关联，不自动重新创建付费任务，不立即删除可能正在被读取的图片 |
| 上游已返回任务编号，之后绑定失败 | 保留已得到的任务编号和原图片，记录关联恢复异常；不能将已受理当成未提交而重复创建 |
| 进程重启或蓝绿切换 | 持久目录和固定签名密钥保持一致，继续验证原链接；Redis 记录仍按原到期时间处理 |
| Redis 记录提前丢失 | 图片读取失败并告警，不因文件存在就免鉴权开放；不从磁盘清单擅自重建用户归属 |
| 图片文件提前丢失 | 返回缺失错误并告警，不能假装 URL 可用或自动发起新生成 |

当前视频代码在绑定失败时仍保留已接受的任务 ID 并记录日志，本方案要求继续避免重复创建；完整的绑定恢复、提交结果待确认以及费用对账契约在后续视频适配章节明确。[C3]

## 13. 资源消耗与容量控制

图片存在服务器，因此请求增多会增加磁盘占用、磁盘 I/O 与网络流量。7 天清理限制的是保留窗口，不代表容量永远固定。

正常清理下的估算公式：

```text
参考图占用 ≈ 每日上传张数 × 平均文件大小 × 7 天
```

例如每天 10000 张、平均 2 MiB，7 天 PNG 约占 136.7 GiB，另需考虑清单、文件系统开销及暂存文件。若平均接近 10 MiB，则约为 683.6 GiB。两者是容量算例，不是当前真实业务量。

开发必须提供可配置的参考图总容量限额、磁盘剩余空间阈值、上传及图片解码并发上限、下载并发/带宽控制。达到阈值时拒绝新的参考图上传并告警，不删除仍在 7 天内的文件来腾空间，也不影响已有文件的正常读取。

当前 `backend/internal/handler/openai_videos.go` 使用 `ReadRequestBodyWithPrealloc` 先读取完整请求体，`ParseOpenAIVideoRequest` 随后还会读取上传图片。首版需要在读取前增加本分支的总大小限制和上传并发控制，并减少重复缓冲；不能只改落盘服务就宣称解决了上传内存问题。[C2]

下载使用文件流；上传首版仍有受限请求体缓冲，PNG 解码也会占用内存。若后续改为网络到磁盘的全程流式上传，需要同步调整 multipart 解析和现有内容审核所需的图片读取方式，另行评估原生视频转发兼容，不能为了存图跳过审核。

需要监控：目录字节数和文件数、上传失败数、验签失败数、有效链接读取失败数、清理失败数、到期但未删除的积压量。具体容量和并发数在部署时根据真实机器余量配置，不当作行业统一默认值。

## 15. 验收条件

1. 单张合规 PNG 可完成接收、落盘、Redis 登记和签名 URL 生成；生成前不要求已经有上游任务 ID。
2. 从服务器外部使用完整 URL 发起 GET/HEAD，能够取得正确图片；返回字节的 SHA-256 与原上传一致。
3. 改动图片编号、`expires`、`kid`、签名，或添加重复参数，均不能取得图片。
4. 不带签名不能读取；不能通过其他静态路径直接访问磁盘文件，也不能通过路径穿越读取其他文件。
5. 使用可控制的测试时钟验证：7 天前可用，到达 `expires_at` 后拒绝新请求；不实际等待 7 天。
6. 文件、URL、Redis 图片记录共用同一个到期值，补填任务编号及多次查询不续期。
7. 多次读取有效链接成功，上游的 HEAD 探测和后续 GET 不会因“一次性消费”而失败。
8. 重启、重建与蓝绿切换后，原链接在原有效期内继续可用；签名密钥不被重新生成。
9. 密钥轮换后，新链接使用新版本，尚未到期的旧链接仍可验证。
10. 模拟 Redis 登记失败、磁盘满、写入中断时，不向上游提交生成请求；没有永久残留半成品。
11. 模拟 Redis 图片记录消失后，过期文件仍能依靠磁盘清单清理；Redis 连接故障不会触发公开访问。
12. 清理任务停机后恢复，可以补扫过期文件；正常运行时到期文件在下一轮清理中删除。
13. 检查 Caddy、应用及上游请求错误日志，均不泄漏完整签名 URL、签名密钥或 API Key。
14. 图片入口本身可用不等于上游适配完成。先执行不付费的外网读取验证，再确认脑生云的角色、图片拉取时机和旧接口格式；付费生成测试按另行确认的最低配置进行。

## 18. 第二部分范围：创建与状态查询协议转换

## 19. 上游协议怎样选择

### 19.1 账号级显式配置

在上游账号配置中拟新增 `video_protocol`，后端校验允许值，后台在视频相关账号配置处提供选择项：

| 配置值 | 含义 | 创建与查询入口 |
|---|---|---|
| `openai_videos` | 现有原生视频协议 | 继续使用当前 `/v1/videos` 逻辑 |
| `naoshengyun_legacy` | 脑生云旧视频协议 | 通过旧协议适配器使用 `/v1/video/tasks` |

### 19.2 创建与查询使用不同的选择来源

创建时仍执行当前分组、模型权限、账号能力与调度规则；选定账号后，根据该账号的 `video_protocol` 选择转换器，不仅凭模型名或域名猜测。

选中旧协议账号后，在发送前校验已支持字段的必要性、类型和取值；旧协议没有映射的额外生成字段过滤后继续提交，不转发上游。首版不在已选账号间进行复杂的规格试探或付费创建后切换。

查询时使用任务创建时固定的协议及原账号，不重新调度。后来修改账号的协议配置，不能让原任务改走另一条查询路径。账号被禁用、移出原分组或不可用时，按现有可用性校验报错，不自动换其他账号查询。[C2][C3]

不得在旧接口返回 404、超时或 5xx 后再改用 `/v1/videos` 创建同一个任务；反向尝试同样禁止，因为前一次请求可能已经受理并收费。

## 20. SEP 到 Longdao 的创建契约

### 20.1 请求入口与请求头

```http
POST /v1/videos
Authorization: Bearer <原Longdao Key>
X-Client-Request-ID: <SEP clientRequestId>
Idempotency-Key: <SEP clientRequestId>
X-Video-Pricing-Version: <Longdao报价返回的版本>
X-Video-Operation: text-to-video 或 image-to-video
```

文生视频使用 JSON，图生视频使用 multipart。不能在代码中把 multipart 强行声明为 JSON，也不能把文件内容或 base64 直接塞给只接受图片 URL 的旧协议。[C1][C7]

### 20.2 字段与类型

| 输入字段 | 输入形式与约束 | 本次适配规则 |
|---|---|---|
| `model` | JSON 字符串或表单字符串 | 必填，保留原始名称，另行解析显式映射 |
| `prompt` | JSON 字符串或表单字符串 | 首版沿用当前要求的非空提示词 |
| `seconds` | JSON 正整数或表单中的整数字符串 | 必填，解析后为整数，不接受小数或智能时长 `-1` |
| `resolution` | 字符串 | 必须符合选定模型和计费维度，不默默纠正成其他档位 |
| `aspect_ratio` | 字符串，可选 | 提供时验证并传递；省略时不擅自补成某种画幅 |
| `generate_audio` | JSON 布尔值，表单为 `true`/`false` | 严格解析，不能把字符串 `false` 当成真；不提供时不声称已经固定音频结果 |
| `input_reference` | 单张 PNG 文件 | 图生必填、文生不接受，按第一部分保存并取得签名 URL |
| `size` | 可选的完整像素宽高 | 只用于与 `resolution`、画幅做一致性检查，不作为旧接口未声明的顶层参数转发 |
| `fps` | 可选帧率 | 旧契约没有已确认的对应字段，过滤后继续提交，帧率由上游默认决定 |
| `output_format` | 可选格式 | 首版只接受 `video/mp4`，作为交付限制校验，不向旧接口传递未声明参数 |

同一语义的多个已支持字段出现冲突时返回明确错误，不通过“取其中一个”掩盖矛盾。仅脑生云旧协议分支过滤未映射的额外生成字段，JSON 在类型校验前过滤，multipart 表单使用相同规则；日志仅记录被忽略的字段名称，不记录其值。原生 OpenAI 视频协议保持原行为。必填、重复字段、已支持字段的类型及取值、图片格式和大小等检查继续保留；`size`、`output_format` 保留本地交付校验。

`X-Video-Operation` 与是否存在图片必须一致；发生冲突不继续提交。模型目录同步只说明名称可见，不证明此规格、参考图角色或音频能力可以使用。

## 21. Longdao 怎样构造旧接口创建请求

### 21.1 字段转换表

| SEP 输入 | 旧接口输出 | 说明 |
|---|---|---|
| `model` | `model_id` | 默认使用相同模型名，仅应用后台明确配置的映射 |
| `prompt` | `params.content[]` 的 `type: text`、`text` | 首版恰好一个文本项 |
| `seconds` | `params.duration` | 转换为 JSON 整数 |
| `resolution` | `params.resolution` | 传已验证且与报价一致的值 |
| `aspect_ratio` | `params.ratio` | 有值才传 |
| `generate_audio` | `params.generate_audio` | 有值才传，保留 true/false 原意 |
| `input_reference` | `params.content[]` 的 `type: image_url`、`image_url.url` | 使用 Longdao 本地文件签名 URL |
| 图生角色 | 图片项的 `role: reference_image` | 按用户已确认的要求固定，不改为 `first_frame` |

根据旧文档，`reference_image` 属于参考生视频的语义，`first_frame` 才是首帧约束。SEP 仍可沿用 `image-to-video` 操作名，但本适配不会向用户保证上传图片就是视频第一帧。[R8]

### 21.2 文生视频示例

以下为结构示例，不代表该模型和规格已经通过付费调用验证：

```json
{
  "model_id": "seedance-2.0",
  "params": {
    "content": [
      { "type": "text", "text": "清晨草地上的露珠，镜头缓慢推进。" }
    ],
    "duration": 4,
    "resolution": "720p",
    "ratio": "16:9",
    "generate_audio": true
  }
}
```

### 21.3 图生视频示例

```json
{
  "model_id": "seedance-2.0",
  "params": {
    "content": [
      { "type": "text", "text": "让参考图片中的草叶随风摆动。" },
      {
        "type": "image_url",
        "image_url": { "url": "<Longdao生成并保存到Redis的7天签名URL>" },
        "role": "reference_image"
      }
    ],
    "duration": 4,
    "resolution": "720p",
    "ratio": "16:9",
    "generate_audio": true
  }
}
```

### 21.4 上游鉴权与请求限制

旧接口地址为脑生云配置的合法上游基地址加 `/v1/video/tasks`，不能在现有 `/v1/videos` 地址后继续拼接一段完整路径。URL 使用结构化 API 构造，并执行项目现有的基地址验证。

上游 `Authorization` 使用选中账号中保存的脑生云 Key，不能转发 SEP 提供的 Longdao Key。原请求的报价版本和操作头由 Longdao 本地解释，不当作脑生云已经支持的参数透传。

旧文档声明创建 JSON 请求体上限 64 KiB。[R8] 图片改为 URL 后请求仍需限制最终 JSON 编码大小，尤其是提示词；超过限制应在本地拒绝，不能先提交再等待上游报错。图片本身 10 MiB 的上限与该 JSON 上限是两件事。

## 22. 规格支持和模型名称的处理

### 22.1 模型名称

内部明确区分两个值：

| 字段概念 | 示例 | 用途 |
|---|---|---|
| `requested_model` | SEP 发来的原始模型名 | 对外响应与用量关联 |
| `upstream_model` | 后台显式映射后实际发给脑生云的名称 | 上游请求及响应身份校验 |

没有显式映射时二者相同。不增加去后缀、猜测别名、自动替换模型的逻辑。若映射目标不在旧接口支持范围内，应在发送前报告配置错误。[R8][C2]

### 22.2 时长、分辨率和可选字段

首版只覆盖普通文生及单张参考图，不引入智能时长、Seedance 2.5 Draft/Final、多图、视频参考或音频参考。这是本次实现范围，不是说上游没有这些能力。

旧文档列出 Seedance 2.0 系列的普通时长为 4 至 15 秒，Seedance 2.5 为 4 至 30 秒；两者还支持 `-1`，但 SEP 当前报价与费用维度要求明确正时长，因此首版不开放 `-1`。[R8][C7]

分辨率、画幅和音频取值根据启用模型的已确认能力建立配置与校验，不能只根据文档某个示例推断全部枚举。参数省略代表采用上游默认，并不代表平台保证了一个具体值。

`fps` 没有已核实的旧协议映射，旧协议分支接收后忽略，不因其值的类型返回不支持错误；其他未映射的额外生成字段同样处理。实际帧率以上游成品为准，不承诺 24/30fps。本轮仅修改算力平台，不修改 SEP；SEP 若仍按请求帧率校验成品，可能标记规格不匹配。被忽略字段不参与幂等语义摘要，同一幂等键仅改变这些字段仍复用原任务。

`output_format=video/mp4` 可作为首版范围检查，但不是旧接口的传参项。其他格式在本地拒绝，不承诺依靠上游自动转换。视频文件的交付和校验见第三部分。

## 23. 创建成功响应怎样归一化

### 23.1 先验证上游受理结果

旧接口文档定义 HTTP 202 与以下响应结构：[R8]

```text
code = 0
message = accepted
data.id = 上游视频任务编号
data.model_id = 创建任务使用的上游模型名
data.status = queued / processing / succeeded / failed / canceled
data.is_final = 是否为终态
data.created_at = UTC Unix秒
```

适配器应验证 HTTP 状态、业务码、任务编号格式、模型、状态及终态标志。不能把任意 HTTP 2xx 或出现一个 `id` 字段就当成完整成功结果。异常格式不能标记为“确定未提交”，因为上游可能已经创建了任务。

### 23.2 转换给 SEP 的结构

创建接口正常受理时，Longdao 返回 HTTP 202，示例为：

```json
{
  "object": "video",
  "id": "<data.id返回的原任务编号>",
  "model": "seedance-2.0",
  "status": "queued"
}
```

| 对外字段 | 数据来源与约束 |
|---|---|
| `object` | 固定 `video` |
| `id` | 原样使用合法的上游 `data.id` |
| `task_id` | 首版可不返回；如果返回，必须与 `id` 完全相同 |
| `model` | SEP 原始请求模型名，而非映射后的名称 |
| `status` | 按第 26 节转换，不固定假设一定处于 queued |
| `progress` | 上游没有提供真实进度时省略，不编造百分比 |

SEP 当前 `TaskSchema` 要求 `object`、`id`、`model`、`status`；提交时还会检查返回模型与原始请求模型一致，因此恢复原始模型名是契约要求。[C7]

Longdao 自己生成并管理请求关联响应头，继续让 SEP 保存 `upstreamRequestId` 用于查账。不能用上游任务 ID 替换计费请求 ID，也不能让上游伪造 Longdao 的关联头或明确拒绝信号。

## 24. 创建关联与新增 Redis 元数据

### 24.1 保持现有绑定兼容

现有“原分组 + 原 Key + 任务 ID 哈希 -> 上游账号编号”继续保留，不把该 Redis 值从数字改成 JSON。[C3]

另外增加作用域相同的任务元数据键，拟定为：

```text
video:task-meta:{group_id}:{api_key_id}:{task_id哈希}
```

| 字段 | 解释 |
|---|---|
| `schema_version` | 记录格式版本 |
| `task_id` | 脑生云原任务编号，也是返回 SEP 的任务编号 |
| `api_key_id` | 原 Longdao Key 的数据库编号 |
| `group_id` | 原分组编号 |
| `account_id` | 创建时选中的原上游账号编号 |
| `protocol` | 创建时固定的 `naoshengyun_legacy` 或原生协议值 |
| `requested_model` | SEP 原始模型名 |
| `upstream_model` | 本次实际请求脑生云的模型名 |
| `reference_asset_id` | 图生使用的 Longdao 图片编号，文生为空 |
| `billing_request_id` | 原创建请求的 Longdao 计费关联编号 |
| `last_status` | 最近一次确认并归一化后的任务状态 |
| `bound_at` | 任务绑定建立时间 |
| `expires_at` | 固定的绑定到期时间 |

元数据与原账号绑定在任务受理后保留 7 天，尽可能在同一 Redis 原子操作中写入并使用同一到期值；查询、补填状态不续期。图片记录仍按第一部分的独立起算点过期，不把两者混为同一个时间。

### 24.2 登记与返回的顺序

正常顺序为：取得并验证上游受理响应 -> 写入原账号绑定和元数据 -> 补充图片 `task_id` -> 返回归一化响应。

如果上游已经受理，后续 Redis 登记失败，必须保留已取得的任务 ID 和受理事实，不转成“确定拒绝”，不重新创建。记录受理后关联降级告警，并在可行范围内短时重试原绑定写入，不能改选账号。

需要明确剩余边界：没有数据库任务持久化时，上游接受之后、Redis 完成登记之前发生进程崩溃，仍存在关联丢失窗口。不能承诺绝对无丢失。恢复依赖同一提交的幂等记录、上游幂等结果或人工排查；没有证据时不自动补发创建请求。上线验收必须覆盖该场景。

## 25. 状态查询的路由与归属校验

SEP 继续请求：

```http
GET /v1/videos/{task_id}
Authorization: Bearer <创建任务时使用的原Longdao Key>
```

Longdao 按以下顺序处理：

1. 验证 Key 与分组，校验任务编号，使用当前 Key、分组及任务编号读取原绑定。
2. 校验原上游账号的状态、能力与分组归属，读取创建时固定的协议和模型元数据。
3. 对 `naoshengyun_legacy` 构造 `GET /v1/video/tasks/{task_id}`；使用原账号的脑生云 Key，不重新调度账号。
4. 验证响应中的 HTTP 状态、`code=0`、`data.id`、`data.model_id`、任务状态和 `is_final`。
5. 校验任务编号与本次查询一致、上游模型与创建时保存的 `upstream_model` 一致；不匹配按协议错误处理。
6. 转换状态，对外 `model` 使用保存的 `requested_model`，返回 HTTP 200 的统一视频对象。
7. 更新最近确认状态时保留原 TTL；临时查询错误不覆盖最近确认的任务终态。

同一个 Longdao 用户换另一把 Key，也无法通过当前绑定校验。上游文档可能允许同一上游用户访问其任务，不改变 Longdao 对外按 Key 隔离的要求。[R9][C3]

已有历史任务可能只有账号绑定、没有新元数据。不能根据后来修改的账号协议猜测它们属于旧协议：历史任务只在可确认原生协议时沿旧路径处理；旧协议所需元数据缺失时报告关联不完整并排查，不自动跨协议试探。

## 26. 状态映射与响应约束

创建响应和查询响应共用一个归一化函数，映射如下：[R8][R9][C7]

| 脑生云状态 | Longdao 对外状态 | SEP 当前对应状态 | 终态 |
|---|---|---|---|
| `queued` | `queued` | `QUEUED` | 否 |
| `processing` | `in_progress` | `RUNNING` | 否 |
| `succeeded` | `completed` | 进入后续成品处理流程 | 是 |
| `failed` | `failed` | `FAILED` | 是 |
| `canceled` | `cancelled` | `CANCELLED` | 是 |

SEP 并不是只要查询得到 `completed` 就已完成最终交付，因此本次只能验收“上游任务完成状态能够传达”，不能把它当成 SEP 已获得可用成品。

查询响应示例：

```json
{
  "object": "video",
  "id": "<与查询路径一致的任务编号>",
  "model": "seedance-2.0",
  "status": "in_progress"
}
```

`is_final` 与状态必须一致；未知状态或终态矛盾不能猜成成功或失败，返回明确上游协议错误并保留已确认状态。任务业务失败时，查询本身仍可成功返回 HTTP 200、`status=failed`，并附经过清理的任务错误信息；不能把“任务失败”与“本次查询 HTTP 失败”混为一谈。

任务失败时保留上游 `error.code` 和脱敏后的具体 `error.message`，不替换为通用的“生成失败”文案；同时记录任务编号、原账号、Longdao Key 编号、模型、计费请求关联编号及脱敏原因。若上游缺少错误原因，明确说明 `status=failed` 但上游未提供 `error.message`，并附任务编号；若缺少错误码，使用 `video_generation_failed`。下载遇到该失败任务时，也在现有不可下载错误中说明上游错误码和脱敏原因。

并发查询更新元数据时采用条件更新，已确认终态不被更早发出、较晚返回的 queued/processing 覆盖。首版仍由 SEP 按现有轮询机制触发查询，不额外部署持续扫描所有任务的轮询器。

## 27. 幂等、重复请求与提交结果不确定

### 27.1 不能只透传一个请求头

旧创建文档已声明 `Idempotency-Key`。[R8] 但上线前仍应验证同键同请求、同键异请求、有效期和作用域的实际行为，不能将文档里出现该头当成所有异常下都不会重复收费的保证。

Longdao 对旧协议创建增加按 `group_id + api_key_id + Idempotency-Key` 隔离的 Redis 提交记录，使用安全摘要生成上游幂等键，避免不同 Longdao Key 恰好使用相同客户端编号时互相干扰。摘要格式和长度在实现时固定并验证，不在其中包含 Key 明文。

该记录拟保存请求语义摘要、选中账号、协议、图片编号及原签名 URL 引用、提交状态、返回任务编号、原计费关联编号和固定到期时间。保留 7 天；若客户端未提供幂等键，不宣称跨请求去重，但仍不在服务内部自动重试不明确的 POST。

### 27.2 重复提交的规则

| 情况 | 处理 |
|---|---|
| 同一作用域、相同幂等键、语义一致且已受理 | 返回原任务与原计费关联信息，不重新上传图片、不重新生成 URL、不再次收费 |
| 同一作用域、相同幂等键、内容不同 | `409` 冲突，在提交前拒绝 |
| 同一请求仍在提交中 | 通过原子状态与短期执行锁防止并发 POST；不再创建第二个任务 |
| 原请求结果不确定 | 保留原账号、请求和图片，进入待确认，不因锁到期直接再 POST |
| 原记录已过 7 天 | 不再承诺本地重复请求识别；客户端不能把过期编号当成永久幂等凭据 |

请求语义摘要应根据原始模型、提示词、实际图片 SHA-256 和各规格生成，不使用 multipart boundary、随机文件名或每次变化的签名 URL 计算“同一个请求”。已登记的请求固定复用原图片及 URL，防止上游认为同一幂等键的请求体发生变化。

任务重放响应必须使用原创建对应的计费关联编号，而不是让 SEP 将新的 HTTP 查询/重试编号误认为另一笔生成账单。实现时针对该创建重放分支明确关联头与用量去重行为；普通请求日志仍可有独立的尝试编号。

上游明确受理后只记录一次生成用量；本地幂等重放和状态查询都不产生第二笔生成费用。并发提交限制、现有内容审核、原计费事务和去重逻辑均须继续经过，不得因新增适配器而跳过。

## 28. 创建错误和查询错误的处理

### 28.1 创建阶段

| 错误 | 处理原则 |
|---|---|
| Longdao Key 或分组权限不足 | 沿用本地 401/403，不调用上游 |
| 参数冲突、字段无法映射、格式不支持 | 400/422，说明具体字段，本地确认未提交 |
| 报价版本失效、模型或计费配置不可用 | 继续使用现有校验与错误契约，不绕过价格确认 |
| 脑生云返回明确的校验拒绝 | 转成 Longdao 统一错误结构，保留清理后的上游原因，只有确认未受理才能标记明确拒绝 |
| 脑生云返回 401/403 等账号问题 | 明确为上游调用失败，不能伪装成 SEP 用户没有登录；记录原账号及上游状态 |
| POST 超时、连接中断、5xx 或无法核验的成功响应 | 视为可能受理，不能标记确定未提交，不自动换账号或重新 POST |

`X-Video-Dispatch` 等明确拒绝标志由 Longdao 控制，不能透传脑生云同名头。本地已经发送上游后，不应仅凭收到一个错误状态就自动释放资金；最终账务处理沿用证据核对机制并单独验收。

### 28.2 查询阶段

| 情况 | 对任务状态的影响 |
|---|---|
| 上游任务明确 `failed` | 返回任务对象和 `status=failed` |
| 上游任务明确 `canceled` | 返回任务对象和 `status=cancelled` |
| 原 Key/分组下没有任务绑定 | 返回任务不可访问/不存在；不更换账号搜索 |
| Redis 不可用或元数据缺失 | 返回服务或关联错误，不能认定生成失败 |
| 脑生云 404 | 表示本次未取得可访问任务，不直接转换为视频 `failed` |
| 查询超时、429、5xx | 返回临时查询错误，不覆盖原状态，不触发新的创建 |
| 任务编号、模型不匹配或未知状态 | 上游协议错误，不把不属于该任务的数据返回给 SEP |

对上游超时等故障使用清晰的网关错误，对限流携带可用的重试提示；不将所有上游状态码不加解释地原样透传。日志保留操作、任务编号、原账号、协议和请求关联编号，并清理密钥、提示词敏感内容及图片签名 URL。

## 30. 第二部分验收与后续边界

### 30.1 使用模拟上游完成的验收

1. 文生 JSON 和图生 multipart 均能解析，字段和数据类型按转换表构造，图片使用 `reference_image`。
2. 图生创建发出之前，签名图片 URL 已可读取；文生不会创建无用图片记录。
3. 显式协议选项可保存和回显；原生账号沿原路径；旧协议账号只调用旧创建、查询路径。
4. 模型名称不自动改写；显式映射时对上游使用目标名，对 SEP 返回原名，并保存两者。
5. 创建 202 响应转为 SEP 可解析的任务对象；缺少 ID、业务码错误、模型错误等不被误判正常受理。
6. 五种状态在创建与查询响应中使用同一映射；取消状态的 `canceled/cancelled` 拼写正确。
7. 查询使用原 Key 作用域、原账号和原协议；更换 Key、修改协议或移出分组不会绕过原绑定要求。
8. 任务元数据与原绑定保留 7 天，查询不续期；图片保留原来的起算点。
9. 查询超时、429、404、5xx 与协议错误不变成业务 `failed`，不触发 POST、不重复记费。
10. 同键同请求返回原任务、原计费关联；同键异请求冲突；并发提交和待确认请求不创建第二个任务。
11. 原幂等请求重复进入时复用同一图片及 URL，不因随机 boundary 或新签名改变请求身份。
12. 覆盖上游受理后 Redis 故障、进程崩溃窗口、终态与运行态并发乱序、历史元数据缺失等场景，明确可恢复能力和残余限制。
13. 旧协议下 JSON 和 multipart 的 `fps` 及其他未映射字段被过滤，不转发、不影响同一幂等请求重放；原生协议仍保留这些字段。非法的已支持字段、格式、时长或冲突尺寸在发送前明确拒绝；最终旧 JSON 超过 64 KiB 也本地拒绝。
14. 用真实 SEP 的 `TaskSchema` 或等价集成测试验证创建与查询响应，避免只测试 Longdao 自己定义的结构。

### 30.2 真实上游验证与本次边界

开发阶段先使用模拟上游及不收费检查，不能为验证转换自动触发真实生成。真实创建会产生费用，测试需使用用户确认的最低配置，验证文档与实际部署的一致性。

本部分验收覆盖创建和查询，第三部分补充下载与成品交付验收。只完成创建、查询，或者只收到 `completed` 状态，都不能作为用户已经取得可用视频的结论。

## 31. 第三部分范围：视频下载适配

本部分按已讨论并确认的下载方案追加，仍是开发设计，尚未修改业务代码或服务器配置。

目标：SEP 继续通过 `GET /v1/videos/{task_id}/content` 向 Longdao 获取完整视频文件。对脑生云旧协议，Longdao 改为“查询任务取得临时 URL，再请求文件并转发”；原生协议保留当前直接向上游 `/content` 取文件的流程。

| 模块 | 本次要求 |
|---|---|
| SEP 下载请求 | 继续使用现有 Longdao 下载路径及原 Key |
| SEP 视频保存与校验 | 继续使用已有本地缓存和文件校验流程 |
| Longdao 下载入口 | 保留现有接口，内部根据创建时固定的协议分支处理 |
| 脑生云旧协议分支 | 实时查询原任务，取得 `data.video_url`，校验并获取文件 |
| Longdao 视频存储 | 流式转发，不新增视频成品的本地持久副本 |
| 计费 | 下载与重试不创建生成任务，计费结算策略沿用原机制 |

图片的 7 天本地保存规则不自动扩展到视频成品。脑生云的临时视频 URL 也不能设定成平台自己签发的 7 天链接。[R9]

## 32. 当前下载流程与改动边界

### 32.1 当前代码的两段下载

第一段是 SEP 后端取回视频：

```text
SEP 查询任务，收到 completed
  -> SEP GET Longdao /v1/videos/{task_id}/content，携带原Longdao Key
  -> Longdao 通过Redis绑定找到原上游账号
  -> Longdao GET 上游 /v1/videos/{task_id}/content，携带上游Key
  -> 上游视频字节经Longdao流式返回SEP
  -> SEP 写入本地暂存文件并校验
  -> SEP 发布本地成品及outputId，更新任务状态
```

第二段是用户从 SEP 读取成品：SEP 验证登录用户、任务归属、`receiptId`、`outputId` 和有效期，再从自身文件缓存返回视频。正常情况下这一步不再访问 Longdao 或脑生云。[C8]

当前 Longdao 下载逻辑不读取 `video_url`，而是假定上游提供 `/content` 文件接口；本次改动针对这个假设。[C2]

### 32.2 SEP 需要继续满足的文件契约

| 项目 | 当前行为 |
|---|---|
| HTTP 响应 | 完整下载要求 200，不能只有重定向或链接 JSON |
| 类型 | 接受 `video/mp4` 或 `application/octet-stream` |
| 大小 | 最大 256 MiB，存在 Content-Length 时检查，传输中也累计检查 |
| 完整性 | 校验实际长度，计算 SHA-256，检查 MP4 文件特征 |
| 视频结构 | 使用 ffprobe 检查格式、尺寸、时长、帧率和音频 |
| 成品发布 | 下载及文件校验完成后才登记可用输出 |
| 缓存窗口 | 当前在首次确认上游完成时设置 24 小时窗口，不是每次下载续期 |

本次不更改 SEP 的这些现有要求。Longdao 仍返回文件字节，不让 SEP 改成处理脑生云临时 URL，也不让浏览器直接跳转脑生云下载。[C8]

## 33. 旧协议下载的执行顺序

1. 接收 SEP 的 `GET /v1/videos/{task_id}/content`，验证原 Longdao Key、分组、任务编号和现有并发限制。
2. 根据原绑定取得上游账号及固定协议。对原生协议进入现有逻辑；对 `naoshengyun_legacy` 进入专用下载逻辑，不重新选择账号。
3. 使用原账号的脑生云 Key 请求 `GET /v1/video/tasks/{task_id}`。
4. 使用与状态查询相同的解码和身份校验规则，确认 `code=0`、任务 ID 相符、上游模型相符、状态为 `succeeded` 且终态标志正确。
5. 读取非空的 `data.video_url`。若尚未成功或没有可用地址，按第 37 节返回错误，不尝试下载未知内容。
6. 校验该 URL，使用专用文件下载请求获取视频，不能直接复用会附带上游 Key 和账号头覆盖的任务查询请求。
7. 在向 SEP 发送响应头之前，检查文件 HTTP 状态、类型、声明长度及基本 MP4 文件特征。
8. 检查通过后向 SEP 返回完整文件的 HTTP 200 响应，边读取上游边写出，并持续限制字节数与传输期限。
9. 成功结束或失败取消后关闭上游响应体，释放并发名额和连接；不遗留视频文件或无效后台传输。

任务查询与文件下载是两个 HTTP 请求：前者需要上游 Key，后者默认依靠完整临时 URL 授权。除非供应商明确给出其他要求，不向文件存储/CDN 地址附带任何 API Key。

## 34. 临时 URL 的处理与访问限制

### 34.1 获取和使用方式

旧查询文档说明成功任务返回临时视频地址，并明确要求不要缓存或公开该地址。[R9]

| 项目 | 处理规则 |
|---|---|
| 获取时机 | 每次文件下载操作实时查询原任务 |
| 保存范围 | 仅供本次下载及其受限重试使用，不长期写入 Redis 或数据库 |
| 签名参数 | 原样保留供应商 URL 的有效查询参数，不自行追加、删除、排序或重新签名 |
| 对外暴露 | 不放进返回 SEP 的视频对象，不通过 Location 让客户端跳转 |
| 鉴权头 | 文件请求不附带 Longdao Key、脑生云 Key、Cookie 或账号配置的敏感头 |
| 过期时间 | 服从上游实际有效期，不承诺与 Longdao 7 天任务绑定一致 |
| 日志 | 只记录任务、阶段、主机等诊断信息，清理完整 URL 及查询参数中的凭证 |

本地参考图 URL 是平台自己生成的签名链接；这里的成品 `video_url` 由上游生成。两种链接的签发方、保存方式和期限不同，不能混用第一部分的签名服务。

### 34.2 下载地址校验

下载器只接受通过检查的 HTTPS 地址；拒绝 URL 用户名密码、非预期端口及本地文件等非 HTTP 协议。供应商实际下载域名或 CDN 域名通过部署允许列表明确配置，不直接假设文件一定放在 API 域名下，也不放行任意公网域名。

校验解析结果与实际连接目标，阻止环回、私有、链路本地、云元数据等非预期地址，包括 IPv6 及映射形式。不能只检查 URL 字符串，或仅在首次解析时检查一次、连接时又不受限制地重新解析。复用项目已有 URL/连接保护时，检查它是否满足本下载器的约束，不能被全局“允许内网”选项绕过。

若上游返回重定向，设置明确的次数上限，每一跳重新验证协议、域名和目标 IP；始终不携带敏感头。未经验证的重定向不能自动跟随。需要代理时，所用代理路径也必须满足相同的目标限制，不得因此绕开检查。

具体允许域名在接入验证时根据供应商确认的地址配置，文档不编造尚未获得的 CDN 域名。地址不符合规则时返回下载地址不受支持的错误，不降级为任意地址代理。

## 35. 文件响应检查与完整下载契约

### 35.1 发出响应前的检查

| 检查项 | 必须满足的条件 |
|---|---|
| HTTP 状态 | 最终文件源返回 200，不能把 403/404/5xx 页面当成视频 |
| Content-Type | 为 `video/mp4` 或 `application/octet-stream`；不接受 JSON、HTML 等错误正文 |
| Content-Length | 如存在，应为合法正整数且不超过 `256 × 1024 × 1024` 字节 |
| 文件起始内容 | 受限预读少量字节，检查与当前 SEP 兼容的 MP4 基本文件特征 |
| 长度一致性 | 传输结束时，实际长度必须与已声明长度一致；没有长度头也要限制累计字节数 |

预读的字节检查后必须原样写给 SEP，不能因为检查文件头而丢失开头内容。传输过程中不解压或转换视频、不重新编码，不把多次失败下载的片段拼成一个文件。

基本文件特征检查不代替完整视频验证。尺寸、时长、帧率、音频及 MP4 结构仍由 SEP 按现有逻辑检查，Longdao 不根据请求规格伪造文件属性。[C8]

### 35.2 返回给 SEP 的响应

首版旧协议分支以当前 SEP 所用的完整文件下载为契约，返回 HTTP 200 和原视频字节。传递已验证的文件类型、可信的长度；设置不缓存和禁止 MIME 嗅探的响应头，不转发供应商 Set-Cookie、鉴权信息或未验证的重定向头。

没有 Content-Length 时允许流式传输，不能编造文件长度。限制和校验始终覆盖实际读到的总字节数。

旧协议首版不增加断点续传承诺，不向文件源转发 Range 或条件请求头，也不把上游 206 当作完整视频交给 SEP。原生协议分支继续保留现有 Range/条件头行为，避免影响既有调用方。

## 36. 超时、流式转发与资源释放

Longdao 不把整个成品读进内存，不先下载到自身持久磁盘；使用受限文件头预读和固定大小传输缓冲区，把上游响应体流式写给 SEP。

需要配置连接超时、TLS/响应头等待期限、读取停滞控制和整体下载期限。整体预算覆盖任务查询、可能发生的一次链接刷新和文件传输，不能让每一阶段都重新获得一个完整总时长。

SEP 当前下载请求使用 180 秒超时，Longdao 应设置小于该值并留有网络及响应余量的整体预算；具体数值在部署配置中确定，使用慢响应模拟验收，不能只设置 TCP 连接超时就认为长传输已受控。[C8]

SEP 取消请求或断开连接时，取消对应上游任务查询/文件下载请求并关闭响应体。释放用户和账号并发名额，不允许客户端已离线而服务器继续无期限接收视频。

开始向 SEP 发送文件后发生错误，应中止文件流并记录“传输中断”，不能向已经开始的视频正文追加 JSON 错误。若先前已发送 Content-Length，必须使客户端能够识别提前结束；没有长度头时也要正确传播传输错误，不能把截断当成正常 EOF。

## 37. 错误、链接刷新与重试边界

### 37.1 错误分类

| 情况 | 对外处理及后续行为 |
|---|---|
| 原 Key/分组下找不到任务 | 按现有任务访问契约返回 404，不搜索其他账号 |
| Redis 或原账号不可用 | 返回关联/服务错误，不尝试其他上游 |
| 原任务仍 queued/processing | 返回尚未就绪的错误，不启动文件请求 |
| 原任务 failed/canceled | 返回任务不可下载的明确错误，不重新生成 |
| succeeded 但没有临时 URL | 返回临时成品不可用，允许之后查询和下载 |
| URL 不符合地址规则 | 返回下载地址校验错误，不执行文件请求 |
| 最终文件源 403/404 | 仅在尚未向 SEP 发出文件响应时，按下一节最多刷新并重试一次 |
| 文件类型、内容或大小不符合约束 | 返回上游文件错误，不尝试绕过校验 |
| 查询或下载超时 | 返回网关超时；如果已经开始传输则中止连接 |
| 传输中断 | 本次失败，保留原任务，允许之后重新取完整文件 |

下载错误必须与上游生成任务失败分开。不能把 `last_status=completed` 改写成生成 `failed`，也不能把取文件失败当作未创建任务。

### 37.2 一次链接刷新的精确范围

初次文件请求最终返回 403 或 404，并且还没有向 SEP 发送文件头或文件字节时，可以重新查询一次原任务，重新执行身份和状态校验，取得当前 `video_url` 后再请求一次文件。

整个操作最多一次刷新、一次文件重试，仍受同一个整体超时预算约束。若再次失败，向 SEP 返回明确错误，不进行无上限重试或切换账号。

一旦开始转发文件，即使之后连接断开或地址失效，也不在同一响应中自动重试。之后的新下载操作从原任务重新查询 URL、从头获取完整视频；SEP 当前暂存文件失败后由其现有清理逻辑回收。[C8]

### 37.3 计费边界

下载、链接刷新和文件重试只能调用查询与文件 GET，不得调用生成 POST，不增加生成用量记录。原有已受理任务的扣费、退款、取消及对账等待策略本轮不调整，也不因下载失败自动退款或重新扣费。

## 38. 工程改动位置与开发顺序

| 工程位置 | 拟开发内容 |
|---|---|
| 现有视频 Handler | 保留下载入口和原 Key 校验，按创建时固定的协议选择处理分支 |
| 旧协议任务查询服务 | 复用第二部分的任务响应解码、模型和任务身份校验，读取当前临时 URL |
| 专用文件下载服务 | 地址及重定向检查、无敏感凭证请求、文件检查、流式传输及受限刷新 |
| 配置与依赖注入 | 配置下载允许域名、地址限制、传输预算及必要的限流，接入已有日志和 HTTP 基础设施 |
| Redis 层 | 读取原任务元数据；不增加临时视频 URL 缓存，不改变原任务 TTL |
| SEP | 复用现有取文件、落盘、校验和用户下载流程，执行兼容验证 |

开发按以下顺序进行：先用模拟上游验证任务查询和地址获取，再完成安全文件请求与流式响应，最后接入原下载入口并执行真实 SEP 兼容测试。不会以“浏览器能打开上游 URL”代替 Longdao 到 SEP 的完整文件验证。

还需复核 Caddy 的请求期限、连接关闭与日志配置是否允许该视频传输，确保不会在应用允许的传输窗口内提前截断，或把完整临时视频地址写入日志。本次不为下载引入新公网端口或视频静态目录。

## 39. 下载适配验收条件

### 39.1 模拟上游验证

1. 原生协议仍直接请求上游 `/content`；旧协议只查询原任务并从返回地址取文件。
2. 原 Key 可以访问原任务，其他 Key 不可访问；查询和文件获取过程中不重新选择账号。
3. 任务查询使用脑生云 Key，文件请求及重定向后均不包含 Longdao Key、脑生云 Key 或账号敏感头。
4. queued、processing、failed、canceled、缺少 URL、任务/模型不匹配等情况，均不会错误返回可用文件。
5. 合法 HTTPS 地址可用；内网目标、非预期域名/协议、危险重定向及超出跳转上限均被阻止。
6. 有长度与无长度两种视频响应都可完整转发，预读头部没有丢失，返回字节 SHA-256 与源文件一致。
7. 文件源返回 HTML/JSON、非法长度、超大文件、伪 MP4 或中途断开时，本次下载失败，不能登记为有效交付。
8. 初次文件请求 403/404 仅在未发送文件前刷新一次；刷新仍失败后退出，不循环重试。
9. 开始传输后断开，不拼接重试、不向视频正文写 JSON；之后的新下载可针对原任务重新完整获取。
10. 慢连接、慢响应、传输停滞及客户端主动断开时，期限、取消与连接释放均生效，没有后台残留下载。
11. 不向 Redis/数据库写临时 `video_url`，Longdao 不遗留成品视频文件，日志不泄漏链接与密钥。
12. 下载、刷新与重复下载都不出现新的生成 POST，不重复产生生成费用，原有计费策略不被改变。
13. 原生下载的 Range/条件请求行为不回退；旧协议完整下载返回 200，不误交付部分响应。

### 39.2 SEP 兼容与完整流程验收

使用真实 SEP 下载适配器验证 HTTP 状态、文件类型和 256 MiB 上限，确认其能够完成本地落盘、SHA-256 计算、ffprobe 校验并登记 `outputId`。随后由有权限的 SEP 用户通过原文件接口获取本地视频，无权限用户不能获取。[C8]

参考图处理、创建请求、状态查询和本次下载必须连成一条可验证链路。只有上游返回 succeeded、Longdao 能获取文件、SEP 校验并保存成功、用户能获取对应成品，才算端到端视频适配通过。

开发及模拟测试不发起付费视频生成。真实上游测试沿用用户确认的最低配置和费用约束，不因补充下载模块自动创建新的付费任务。本轮完成的是开发方案，实施、部署和验收仍须实际执行。
