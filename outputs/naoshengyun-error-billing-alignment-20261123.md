# 脑生云接口错误状态与扣费核对

核对日期：2026-11-23。

范围：脑生云公开接口文档，以及 LongdaoAI 本地 main（`761dcc47`）中的实际转发与计费入口。未修改业务代码，未调用付费模型，未读取真实密钥、账务或生产配置。因此本文确认代码行为与公开契约，不认定某一笔线上请求已扣费或已退款，也不认定生产账号正在使用所有兼容分支。

## 1. 核心结论

1. 公开文档没有提供完整的“错误码或任务状态 → 是否扣费/冻结/退款”规则表。不能把 `400/403/429/500/502/504` 直接转换成扣费结论。
2. 必须分开核对三层资金：脑生云扣上游账号额度、Longdao 扣算力用户额度、SEP 的预留/结算。三层并非同一个事务，也没有自动共享账务状态。
3. 旧视频协议成功受理后，Longdao 就提交本地计费任务；没有等视频生成完成。之后查询得到 `failed/cancelled`，该查询链路没有自动退款或同步脑生云退款结果的逻辑。实际扣费是否提交成功仍应查询本地账务证据。
4. Longdao 的图片/视频单请求用量接口查本地 PostgreSQL 的用量与计费事务证据，不查询脑生云流水。其 `settled` 不代表上游账务已对齐；`pending` 不代表未扣费。
5. 需要上游补充可按 request_id、task_id 或 Idempotency-Key 核查的账务凭证，以及失败/取消/超时的结算规则，才能从源头建立可靠判定。

## 3. 当前代码使用的接口

路径表示 Longdao 可执行的转发分支；实际域名、所选账号及协议仍依赖生产配置，不在本文猜测。

| 能力 | SEP → Longdao | Longdao → 脑生云或文件源 | 扣费信息是否随业务响应明确提供 |
|---|---|---|---|
| 聊天 | `POST /v1/chat/completions`，或兼容 Responses/Messages 入口 | API Key 账号可直转 chat/completions；其他入口或分支可能请求 Responses/Messages，不能认为总是原路径透传 | 已读公开文档未说明每类错误是否计费；token usage 也不是金额结算凭证。 |
| 文生图 | `POST /v1/images/generations` | API Key 图片分支使用同名路径 | data/usage 不是带有扣费终态的流水。 |
| 图生图 | `POST /v1/images/edits` | API Key 图片分支使用同名路径 | 新版文档没有错误与账务状态表。 |
| Seedance 旧协议创建 | `POST /v1/videos` | 当账号 `video_protocol=naoshengyun_legacy` 时，转成 `POST /v1/video/tasks` | 202 只证明受理或命中幂等结果，不说明已扣、冻结或待结算。 |
| Seedance 旧协议查询 | `GET /v1/videos/{id}` | `GET /v1/video/tasks/{id}` | 文档公开任务对象没有 charge_status/amount/refund_status 等账务字段。 |
| Seedance 旧协议下载 | `GET /v1/videos/{id}/content` | 查询原任务，取得 video_url 后从文件源下载；源站首次 403/404 时有一次刷新重试 | 文件状态码不代表生成账务状态；没有新增视频创建请求。 |
| 图片/视频报价 | `/v1/sub2api/images/pricing`、`/v1/sub2api/videos/pricing` | 使用 Longdao 本地价格与配置，不是脑生云报价转发 | quoted 表示本地可用报价，不表示已收费。 |
| 图片/视频账务查询 | `/v1/sub2api/usage`、`/v1/sub2api/videos/usage` | 查询 Longdao 自己的 PostgreSQL | 反映本地已确认记录或证据不足，不证明脑生云是否扣费。 |

脑生云同时保留旧、新视频文档。当前重点是已实现的旧协议适配；新版 `/v1/videos` 文档里的错误规则不能自动用于 `/v1/video/tasks`。

## 4. 旧版视频：状态和扣费能确认到哪一步

以下 HTTP 均首先指脑生云接口；它可能被 Longdao 包装为另一个 HTTP 状态。

| 上游结果 | 官方说明/业务含义 | 能否直接断定脑生云扣费 | Longdao 当前行为 |
|---|---|---|---|
| 创建 202，code=0，返回有效任务 | 已创建或命中幂等结果 | 不能；没有明确冻结/扣款时点或金额 | 验证任务身份并绑定 Redis，返回 202；随后提交本地计费。相同幂等键命中已有受理回执时不重新创建、不再次走该计费入口。 |
| 创建 400 | 参数、模型或能力不支持 | 文档没有正式“不扣费”承诺；通常前置拒绝的判断仍需上游确认 | legacyRequest 返回错误，创建 handler 不进入正常计费。不能由此反推上游流水。 |
| 创建 401 | Key 缺失、无效、禁用或关联用户无效 | 文档未定义账务结果 | 同上。 |
| 创建 402 | Key 额度或组织余额不足 | 文档未说明是否有前置冻结、部分执行或冻结释放 | 同上。不能把原有其他任务扣费与本次拒绝混为一谈。 |
| 创建 403 | Key 过期、访问限制或组织不满足条件 | 文档未定义账务结果 | 同上。 |
| 创建 413 | 请求超过 64 KiB | 文档未正式声明扣费规则 | 同上。 |
| 创建 429 | 组织/成员视频并发达上限 | 文档未给“不受理/不扣费/释放冻结”契约 | 对外可保留 429；不进入本次正常计费，派发后的幂等记录可能仍为 unknown。 |
| 创建 500 | 内部处理失败 | 不能；不知道发生在创建、派发或计费之前还是之后 | 常包装 502，保存提交 unknown，不进入正常计费。 |
| 创建 503 | 服务、模型、计费配置或定价暂不可用 | 不能；没有阶段和账务终态承诺 | 常包装 502，保存提交 unknown，不进入正常计费。 |
| 创建超时、断网、回执 JSON/任务身份校验失败 | 可能已受理但回执不可用 | 不能 | 返回 502/504 等，提交标记 unknown；不能换新幂等键盲目重提。 |
| 查询 200，queued/processing | 原任务排队/处理中 | 不能判断是否冻结或已扣 | 转为 queued/in_progress；本次查询不再次计视频创建费，原创建可能已完成本地扣费。 |
| 查询 200，succeeded | 原任务完成 | 业务成功不等于已取得账务凭证 | 转为 completed，下载与本地账务分别核对。 |
| 查询 200，failed | 原任务失败，error 可有 VIDEO_UPSTREAM_TASK_FAILED/VIDEO_TASK_FAILED | 不知道是否退费、部分收费或退款处理中 | 转为 failed 并保留原因；查询函数没有自动退款动作。 |
| 查询 200，canceled | 原任务取消 | 不知道取消是否收费、何时解冻/退款 | 转为 cancelled；查询函数没有自动退款动作。 |
| 查询 404 | 不存在或不属于当前上游用户 | 不证明此前未提交/未扣费 | 对外可为 404；还要区分本地 Key 归属/Redis 7 天过期导致的 404。 |
| 查询 500/503 | 查询失败或成品暂不可用 | 不能否定原任务及已发生费用 | 查询失败不是生成失败；本次查询不重复创建计费。 |
| 文件源 403/404、下载超时、文件断流 | 权限、临时链接、文件源或传输问题 | 不能；原视频可能已成功并收费 | 下载不触发新的创建计费，不会因下载失败自动撤销原计费。 |

重要限定：“不进入正常计费”只描述当前创建 handler 收到错误后的代码出口，不是对客户端所见某个 HTTP 状态的全局承诺。重试、已有任务、先前已扣费、部分图片成功及写响应失败等均须按原请求关联核对。

## 5. 图片、语言模型与流式失败

### 5.1 图片

- D05 列出 400/401/429/500，但未说明这些失败的扣费规则；D06/D07 仅列成功响应，更不能补造一张“失败一律不扣费”的表。
- Longdao 的常规图片转发若以错误返回且没有已生成图片结果，会退出该次正常计费入口；但上游可能已经生成或消费资源，本地解析失败/传输失败并不证明上游未收费。
- 已有部分图片输出后流式失败时，代码可保留实际图片数与 usage 并继续本地计费。不能向 SEP 承诺“看到失败就一定不扣费”。
- HTTP 200 可包含业务 error；图片保活也可能先发送 200 再返回错误。HTTP 状态不能作为图片成功或扣费的唯一依据。
- D09 的 quota 是新版异步图像任务的结算额度。文档明确 0 可能为“尚未结算或免费”，没有同时给出可唯一判定的结算终态/退款字段。该协议目前没有接入同步图片链路进行对账；不能为了解决当前问题直接改用其字段。

### 5.2 语言模型、Responses/Messages、SSE

- 已读公开接入文档没有给出“生成中断、客户端主动取消、部分 token 输出、模型拒答、流内业务错误”的逐项收费承诺。
- token usage 是模型用量，不能自动等同于脑生云实际扣款金额；本地价格、倍率也可能与上游价格不同。
- 已发请求或收到部分输出后断流，不知道上游是否继续计算/完成计费。反过来，200 响应头也不说明流完整成功。
- 本地计费按各协议最终产生的结果/usage 进入记录流程，不能给所有流式失败统一“不扣费”结论。此前明确暂缓的部分 Anthropic/Gemini 流内错误转换问题仍在本次核对边界之外。

## 6. 本地账务证据的准确含义

| 字段或接口 | 可确认的含义 | 不能推出的结论 |
|---|---|---|
| 本地报价 pricing_status=quoted | Longdao 当前规格有有效价格 | 不能证明已派发、已扣款。 |
| `/v1/sub2api/videos/usage` status=settled，actual_cost_usd 为正 | 关联请求存在符合当前校验条件的本地用量和已提交计费事务标记，金额是算力用户的本地费用 | 不是脑生云费用；不是视频一定完成；也不代表上游没有/已有后续退款。 |
| 同接口 status=settled，金额为 0 | 符合当前接口判据的本地结算金额为 0 | 不证明脑生云免费；不证明 SEP 已释放预留。 |
| 同接口 status=pending，金额 null | 当前无法给出可确认的本地结算金额：可能未记录、尚未落库、缺记录、关联歧义、模式不符等 | 不能直接解释为未扣费，也不能断言一定会自动变为 settled。 |
| `/v1/sub2api/usage` 图片 settled/pending | 同类本地证据，图片另有 pending_reason | 不能用未查到记录证明上游没扣款。 |
| 本地用量日志存在 | 有用量记录 | 单凭日志不证明扣费事务提交成功；接口还会检查 dedup/归档事务标记。 |
| 上游 billing probe | 可选探测 `GET /v1/sub2api/billing`，保存元数据快照 | 它不是按 task_id/request_id 查询上游扣款流水；公开目录没有承诺脑生云支持这条接口。未核实其生产启用状态。 |
| 余额前后变化 | 某时间段的总净变化 | 并发任务、充值、退款、冻结、多人共用额度会混入，不能准确分配给某个请求。 |

关联时分别保存 SEP 请求 ID、Longdao 响应 X-Client-Request-ID、账务 request_id（媒体适配器常为 `client:<响应头值>`）、上游 request_id、视频 task_id。不要拿 task_id 替代本地账务 request_id；创建失败拿不到 task_id 时，尤其需要上游支持按幂等键/请求 ID 查询。

## 8. 当前可对 SEP 说清楚的边界

- 本地明确未调用上游的前置拒绝，例如上传参数校验、参考图存储初始化失败、报价核验拒绝，该次生成没有向脑生云派发，也没有进入本次创建的正常计费入口。仍应关联原请求，避免把已有受理任务的重试误认为新请求。
- 已派发但超时、5xx、回执解析错误，应记为账务待核实，不能靠状态码断定未扣费。
- 视频已受理后生成失败、查询失败、下载失败，应保留任务状态和账务状态分别核对。现有本地流程存在“任务失败但创建费用已记录”的可能，不能把任务 failed 当退款凭证。
- 已确认的本地费用使用现有 usage 查询；上游费用需要其流水或正式契约确认。两个金额可以不同，不做直接相等假设。
- 当前 pending 接口没有明确的“最终确认未收费”状态，这是客户端仅靠现有返回难以准确关闭对账流程的一个实际限制。是否改协议/计费时点，应等上游规则确认后单独制定方案。
